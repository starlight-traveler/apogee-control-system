Post-flight analysis

Replay workflow.

The data logger writes a binary record of what the firmware knew at each loop. Replay decodes that record, reruns estimator and predictor logic, and lets you compare logged decisions against the current code.

Workflow

Decode to plot
01 log

Record binary telemetry

Firmware writes dense telemetry records and sparse event records into SENSxxx.BIN on SD.

02 decode

Convert to CSV and events JSON

decode_log.py turns binary records into tabular data that Python and the native replay tool can inspect.

03 replay

Run current code against recorded data

acs_replay can ignore logged state and rebuild the estimator path from raw sensor data.

04 plot

Explain the flight

Plots should show real apogee, predictor values, velocity, baro/state altitude, flap command/effective angle, and confidence flags.

python3 tools/replay/scripts/decode_log.py tools/replay/data/SENS065.BIN -o tools/replay/data/SENS065.csv tools/build/bin/acs_replay tools/replay/data/SENS065.csv --ignore-logged-state --rebuild-main-quaternion python3 tools/replay/scripts/plot_flight.py --flight fullscale_4 --view validation

What to inspect

High signal

First prediction

Check the first coast prediction after holdoff. If it is badly wrong, inspect burnout timing, velocity, attitude, AoA table coverage, and baro/state altitude agreement.

Velocity trace

Vertical velocity tells you whether the estimator believes the vehicle still has enough energy to reach target. Bad velocity usually means bad apogee.

Frame agreement

Compare ICM, LSM, BNO, Pulse, and WT901 gravity vectors on the pad. A sign or rotation error can look like drag-model error during coast.

Predictor flags

Flags explain why a prediction should not be trusted: CFD clamp, step limit, baro-vz guard, angular rate clamp, horizontal speed cap, or high-AoA fallback.

Replay math

Reconstruction

Replay is useful because it separates three different questions: what the sensors measured, what the estimator believed, and what the predictor would command from the current code.

Pad-relative altitude

\(h_{AGL}(t) = h_{baro}(t) - h_{pad}\)

Use AGL for flight decisions and apogee error. Comparing ASL prediction against AGL target creates an error close to pad altitude.

Baro velocity check

\(v_{baro}(t) \approx \frac{h(t)-h(t-\Delta t)}{\Delta t}\)

This is noisy, but it catches cases where the state velocity drifts toward a bad value. The firmware only updates this from fresh baro samples.

Prediction error

\(e_{apogee}(t) = h_{predicted}(t) - h_{actual}\)

Early coast error usually points at burnout timing, velocity, frame/AoA, or drag model coverage. Late error often points at state altitude/velocity convergence.

Energy sanity check

\(h_{ballistic} = h + \frac{v_z^2}{2g}\)

A predictor below the ballistic bound is normal with drag. A predictor behaving like raw state altitude means velocity, drag, or validity gates are suspect.

Corrections to test

Replay flags

Frame correction

Plot pad gravity vectors for ICM, LSM, BNO, Pulse, and WT901. The dominant axis and signs should agree. A frame mismatch can look exactly like an aero-model miss.

Altitude source correction

Compare baro AGL, state AGL, and predictor seed altitude. If prediction is off by pad altitude, inspect ASL/AGL conversion before changing drag constants.

Velocity correction

Plot pre-burnout, burnout, and coast velocity. Bad vertical velocity creates squared error in the no-drag term, so a small velocity miss can become a large apogee miss.

Aero coverage correction

Check CFD clamp flags for ACS angle, AoA, and Mach. Above table coverage should be treated as uncertain, not silently trusted as a precise flap command.
