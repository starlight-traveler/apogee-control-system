Active apogee control

Apogee control software.

This repository is the flight software, calibration workflow, telemetry format, and replay tooling for a Teensy 4.1 active apogee controller. The controller estimates the rocket state, predicts coast apogee, and commands synchronized drag flaps only when the estimator and predictor are healthy enough to trust.

Mathematics in the code

Mental model

The control math starts with the energy picture, then replaces the simple "gravity only" coast with a numerical force model. A no-drag apogee is just current altitude plus remaining kinetic energy divided by gravity. The firmware keeps that as a useful upper bound, but the trusted predictor recomputes drag at each step.

Math pathcoast model
no-drag reference:
    \(h_{\mathrm{apogee}} = h + \frac{v_z^2}{2g}\)

firmware predictor:
    air-relative velocity -> Mach + AoA
    CFD axial/normal force -> density scaling -> acceleration
    flap lag + pitch moment -> changing attitude
    RK4 integration -> refined vertical-velocity zero crossing

Why numerical integration?

Drag is not constant. It changes with Mach, flap angle, AoA, density, and attitude, so one closed-form equation would hide the hard parts.

Why carry flags?

A prediction can be finite and still not be safe to command from. The code carries clamp, stale, step-limit, and uncertainty flags alongside the number.

What the system does

Control objective

The apogee controller is not trying to fly the rocket like a full autopilot. It is trying to answer a narrower question quickly and repeatedly: if the rocket continues coasting from the current state with a given flap angle, where will vertical velocity reach zero?

Estimator

The estimator turns barometer and IMU data into pad-relative altitude, vertical velocity, acceleration, zenith angle, and health flags. It keeps stale samples from pretending to be fresh measurements and publishes confidence signals that the control path can inspect.

Predictor

The predictor rolls the current coast state forward through gravity, wind-relative aerodynamics, CFD table forces, pitch dynamics, and flap latency. The output is a predicted apogee and time to apogee, plus flags when the model had to clamp or fall back.

Controller

The controller evaluates flap angles and chooses a command that moves predicted apogee toward the target. It is deliberately conservative: if the predictor is invalid, uncertain, stale, or outside coverage, the command flows through the normal actuator path toward zero degrees.

Logger and replay

The logger writes dense binary telemetry and sparse event records to SD. Replay tooling decodes those records into CSV and runs the flight computer logic offline, so estimator and predictor behavior can be tested against real flights.

Firmware loop

Hot path
01 read

Acquire sensors

Drivers collect BMP585 pressure altitude, optional MS5611 comparison pressure, fast ICM/LSM IMU data, BNO attitude/reference data, WT901 comparison data, and optional Ellipse/Pulse20 raw IMU logs. Each path carries freshness flags so cached continuity does not become new evidence.

02 frame

Normalize frames

Sensor axes are rotated into the rocket body frame. This matters because attitude from one rail and acceleration from another rail can create a vertical acceleration bias if their frame mappings disagree.

03 fuse

Update attitude and vertical state

The flight computer propagates attitude with gyro data, trims it with guarded reference rails, and updates Kalman filters with fresh acceleration and barometer samples. Ground constraints keep the pad state stable before liftoff.

04 phase

Advance the state machine

Flight phase moves through Ground, Burn, Coast, Overshoot, and Descent. Transitions require confirmed evidence: liftoff uses accel first with a strict baro backup, burnout requires sustained low acceleration while ascending, and descent records the maximum observed altitude.

05 predict

Build a guarded predictor seed

The seed uses vertical Kalman state, bounded zenith, bounded angular rate, and a conservative horizontal speed estimate only when attitude and accel are fresh enough. Suspicious inputs raise confidence flags instead of quietly entering the optimizer.

06 act

Command flaps through the actuator model

Automatic flap motion is gated by phase, post-burn holdoff, baro/state agreement, predictor validity, and actuator state. Commands always pass through clamp, deadband, rate, PWM, and settling logic.

Flight phases

State machine
Ground
Pad altitude is learned, barometer drift is tracked slowly, and vertical state is constrained near zero.
Burn
The motor is adding energy. The predictor may produce telemetry, but it is not yet the final coast model.
Coast
Burnout is confirmed. Apogee prediction and automatic flap control are meaningful after holdoff and safety gates.
Overshoot
Measured altitude is already above target. The rocket may still be ascending, so prediction and attitude propagation continue.
Descent
Vertical velocity has crossed downward. The maximum observed altitude is recorded as apogee.

Apogee predictor

Coast model

The predictor propagates a compact two-dimensional state: altitude, vertical velocity, horizontal speed, zenith angle, angular rate, physical flap angle, and requested flap command. It does not model motor thrust, so burnout detection and post-burn holdoff are launch-critical. 

filtered vertical state     attitude seed          flap state
        |                       |                    |
        v                       v                    v
  altitude / vz -----> predictor seed -----> candidate flap command
                              |
                              v
          wind-relative velocity + atmosphere + Mach
                              |
                              v
              CFD axial/normal force interpolation
                              |
                              v
                 gravity + aero + pitch moment
                              |
                              v
                    RK4 rollout to vz = 0
                              |
                              v
               predicted apogee + confidence flags

Important rule: a better-looking number is not enough. If the integration hits the step limit, the CFD table clamps outside coverage, the seed is stale, or uncertainty bounds spread too wide, the prediction is flagged so actuation can retract rather than keep commanding drag.

Atmosphere

The environment model supplies temperature, density ratio, and wind. Aero uses air-relative speed, not ground speed, so wind is subtracted before Mach and angle of attack are computed.

CFD table

The table is indexed by flap angle, angle of attack, and Mach. It stores absolute axial and normal forces, which are scaled by density ratio and adaptive drag correction before being projected into vertical and horizontal axes.

Integration

RK4 is used for the normal prediction path. The rollout stops when vertical velocity crosses zero, then refines inside the final bracket instead of returning the first descending sample.

Flap control

Drag authority

The flaps are drag devices. More angle generally lowers apogee. Because undershoot is the worse failure mode for this vehicle, uncertain prediction behavior biases toward low drag through the normal command path.

Command angle

The controller-requested angle after clamping and deadband. This is what guidance wants the actuator to chase.

Effective angle

A first-order model of where the flaps have physically moved after servo latency. The predictor uses this to avoid assuming instant drag changes.

First motion

The first automatic deployment is limited by a conservative ramp. This prevents a large initial command before coast state, baro agreement, and actuator feedback have settled.

Late coast

As time to apogee shrinks, command authority tapers and then disables. Near apogee, flap motion can be too late to help and too risky to explain cleanly.

Sensor roles

Rails
Path Role What the flight code cares about
BMP585 Primary pressure altitude Fresh finite altitude defines pad-relative AGL, baro velocity guard, liftoff backup, and state/baro agreement gates.
ICM20948 Fast IMU rail High-rate accel/gyro and optional DMP attitude. Selected ICM attitude should use fresh ICM accel when available.
LSM9DS1 Fast IMU rail Independent accel/gyro/mag observer. Selected LSM attitude should use fresh LSM accel when available.
BNO055 / BNO085 Reference attitude rail Useful as a guarded coast trim after burnout, but not allowed to step the predictor from stale or disagreeing samples.
WT901 Comparison rail Logged in body-frame units for cross-check plots and frame debugging.
Ellipse / Pulse20 Optional high-quality sidecar IMU Raw IMU and mag logs are parsed through bounded serial service, then fused by the same freshness/trust philosophy.

Logging and replay

Post-flight proof

The system is built to be replayed. Binary logs preserve raw rails, selected attitude, filtered state, flap command/effective angle, predictor output, confidence flags, and event records. That lets you inspect whether the flight computer made the right decision from the information it had at the time.

python3 tools/replay/scripts/decode_log.py path/to/SENS010.BIN -o tools/replay/data/SENS010.csv cmake -S tools -B tools/build -DACS_TOOLS_ENABLE_NATIVE_CPP_GUI=OFF cmake --build tools/build --target acs_replay -j tools/build/bin/acs_replay tools/replay/data/SENS010.csv --ignore-logged-state

Use replay for behavior

Replay answers whether the current estimator and predictor would have produced the observed flight decisions from the recorded sensor stream.

Use plots for explanation

Plots should show actual apogee, predicted apogee, state AGL, baro AGL, vertical velocity, flap command, and predictor flags when evaluating a flight.

Launch review checklist

Before flight
  • 01Build the flight firmware cleanly with pio run -e flight.
  • 02Verify flashed settings are correct; SD settings are a mirror/status record, not the boot source of truth.
  • 03Confirm pad barometer reference settles and fresh baro AGL is required before AGL-dependent gates.
  • 04Check ICM/LSM/Pulse frame directions with a static gravity orientation test.
  • 05Confirm no flap motion during Burn and no automatic motion before post-burn holdoff.
  • 06Replay a recent flight and inspect predictor flags, baro velocity guard, command/effective flap angle, and actual apogee alignment.
