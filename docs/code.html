Code highlights.

This page points at the implementation details worth understanding before changing the system. The theme is consistent: compute a useful estimate, carry confidence with it, and let actuator safety logic see the confidence instead of hiding it inside a number.

Predictor core

apogee_model.h

The predictor is structured as a small physics engine. Each derivative evaluation rebuilds air-relative velocity, interpolates CFD force, projects force into state acceleration, advances flap lag, and updates pitch.

Predictor corepseudocode
PredictApogeeWithTime(seed):
    while vertical_velocity > 0:
        next = integrate_one_step(seed, RK4)
        if next.vertical_velocity <= 0:
            return refine_zero_crossing(seed, next)
        seed = next

    if step_limit_hit:
        return ballistic_bound_with_uncertain_flag

Why RK4 here?

Mach and AoA can move fast near burnout. RK4 reduces step-size error without making every control loop do far more tiny steps.

Why midpoint elsewhere?

The flap optimizer has to try many candidate angles. Midpoint is good enough to rank candidates before the expensive bounded validation pass.

Cached CFD interpolation

Table lookup

CFD lookup is repeated constantly: every candidate angle, every RK substage, every loop. The code caches nearby index brackets so repeated interpolation does not search the full ACS/AoA/Mach grids from scratch each time.

axes

Find lower and upper grid cells

ACS angle, angle of attack, and Mach each produce a lower index, upper index, and blend fraction.

corners

Read eight table corners

The force volume is flattened in memory, so the index function maps 3D coordinates into one array offset.

blend

Linearly blend ACS, AoA, then Mach

The order is not magic for linear interpolation, but keeping it explicit makes the table layout easier to audit.

flags

Clamp outside coverage and report it

Out-of-table values are safer as explicit uncertainty than pretend extrapolation.

Estimator to predictor seed

flight_computer.cpp

Zenith clamping

The predictor gets a bounded zenith angle. If raw attitude produces a value outside the trusted range, the value is clamped and the flag follows it.

Horizontal speed guard

Horizontal speed is only seeded when attitude and acceleration are fresh enough. Otherwise, stale tilt is more dangerous than simply omitting lateral energy.

Baro velocity guard

When vertical velocity looks suspect, baro-derived velocity can act as a guardrail. That state is visible to control through confidence flags.

Adaptive drag learning

The learner compares measured vertical acceleration against modeled axial drag only during clean coast, then nudges the active Mach bin without rewriting unrelated regimes.

Actuation optimizer

main.cpp

The control search is built around failure behavior. It tries to find useful drag, but the default answer for stale, uncertain, clamped, or invalid prediction is to request zero degrees through the existing command pipeline.

Actuation commandfailure behavior
if predictor is not trusted:
    target_angle = 0 deg
else:
    rank candidate angles with midpoint prediction
    validate best region with RK4 bounds
    reject candidates with uncertainty flags
    command best angle through servo limits

The important design choice is that "retract" is still just a normal command. The servo layer still applies limits, rate behavior, PWM mapping, and synchronization.

Attitude and rail selection

IMU path
  • Quaternion sanitizemain.cpp normalizes and validates selected attitude before publishing it as the main quaternion.
  • Rail agreementICM, LSM, BNO, Pulse, and WT901 comparisons update trust with hysteresis so source selection does not chatter.
  • Matched accelflight_computer.cpp keeps selected ICM attitude with ICM accel and selected LSM attitude with LSM accel when those samples are fresh.
  • Gyro propagationmath_utils.h uses an exponential-map update so angular rate changes attitude without Euler singularities.
