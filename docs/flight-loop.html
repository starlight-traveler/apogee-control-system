Runtime pipeline

The loop is a set of gates.

The firmware loop is written to keep control authority behind evidence. Measurements must be fresh, frames must be known, phases must be confirmed, and the predictor must stay inside trusted coverage before the flaps are allowed to add drag.

Ground gates

Fresh baro defines pad-relative altitude. Ground constraints keep z and vz near zero. Liftoff requires confirmed acceleration or a strict baro backup: initialized reference, positive altitude, positive baro-derived velocity, and repeated samples.

Burn gates

Burn detection is latched from confirmed liftoff evidence. The predictor can run for telemetry, but it does not model thrust or mass burn, so automatic flap control stays disabled.

Coast gates

Burnout requires minimum burn time, sustained low acceleration, upward velocity, and confirmation samples. After coast starts, a holdoff gives the estimator and attitude path time to settle before first flap motion.

Overshoot gates

Overshoot means measured altitude has passed target. Attitude propagation, BNO coast trim, prediction, and descent detection still continue because the vehicle may be ascending.

Descent gates

Descent is declared when vertical velocity and acceleration gates indicate apogee has passed. The recorded apogee uses max observed altitude so a slightly late transition does not lose the peak.

Critical invariants

Do not break
  • 01Freshness is separate from initialization. A sensor can be online and still stale this loop.
  • 02Selected single-rail attitude should prefer matching fresh accel from the same rail.
  • 03Baro AGL must require fresh finite altitude, not only an initialized pad reference.
  • 04Overshoot still behaves like coast for attitude propagation while ascent continues.
  • 05Presentation smoothing must not delay phase detection or predictor seed logic.
